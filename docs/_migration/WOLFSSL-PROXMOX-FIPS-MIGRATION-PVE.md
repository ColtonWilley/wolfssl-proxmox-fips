# wolfSSL FIPS on Proxmox VE — Migration from an existing Proxmox VE deployment

Use this guide to migrate guests from an existing, non-FIPS Proxmox VE deployment to encrypted storage
configured by the FIPS deployment guides. For guests already on the FIPS deployment, use the Backup
guide.

---

## 1. Before you begin

### 1.1 Requirements

The FIPS destination is a separate, clean installation; an existing node is not converted in place.
For repurposing source nodes, see
[Remove a Cluster Node](https://pve.proxmox.com/pve-docs/chapter-pvecm.html#pvecm_remove_node).

- Destination storage with capacity for the guests being migrated.
- Storage both deployments can reach, or a means of transferring backup archives.
- A shutdown window for each guest.
- An inventory of each guest's disks, firmware, and guest OS.

### 1.2 Sources protected by a Proxmox Backup Server key

`proxmox-backup-client` creates keys with scrypt by default. A node configured to use wolfProvider per
Backup guide §3.1 cannot open a scrypt-protected key file. This applies only to passphrase-protected
keys; keys generated by Proxmox VE for storage definitions have no passphrase and are unaffected.

Convert the key on the source deployment or another host not using wolfProvider:

```bash
proxmox-backup-client key change-passphrase <keyfile> --kdf pbkdf2
```

Enter the current passphrase, then the new one twice. The key's fingerprint is unchanged, so existing
backups remain restorable. The command requires a terminal; for conversion without one, see §5.

Confirm that the key's `kdf` field reads `PBKDF2`:

```bash
grep -o '"kdf":{"[A-Za-z0-9]*"' <keyfile>
```

### 1.3 Conventions

Commands run as `root`, on the node named in each block. `<fips-storage>` is the encrypted Proxmox
storage built by your deployment guide; substitute its name.

## 2. Back up and restore

Repeat this section for each guest. Use a new backup or an existing Proxmox Backup Server snapshot,
including backups from a retired deployment. Backups from LVM-thin, plain or encrypted ZFS, and stock
Ceph use the same restore procedure. Guest firmware, controllers, and drivers are retained; no
conversion is needed.

### 2.1 Record the verification checksum

Inside the running source guest, immediately before the backup in §2.2, record checksums for the
Migration Acceptance guide:

```bash
# in the guest, as root:
date -Ins > /root/pre-migration.stamp
sha256sum /root/pre-migration.stamp <a representative data file> > /root/pre-migration.sha256
sync
```

Use absolute paths and include a file unique to this migration, such as the stamp above, to help
detect a restore from an older backup.

For an existing PBS snapshot, use the verification records from when it was taken; a new stamp will
not be present. Without those records, §4 can check that the guest boots but cannot compare its data
with the source.

### 2.2 Obtain the backup

On the source node, back the guest up
([Backup and Restore](https://pve.proxmox.com/pve-docs/chapter-vzdump.html)). Where the archive already
exists on a Proxmox Backup Server both deployments reach, skip to §2.3:

```bash
# on the source node:
vzdump <vmid> --storage <target> --mode stop
```

If the destination cannot reach the backup storage, transfer the archive to the destination.

### 2.3 Prepare the destination

The destination storage must be unlocked before restoring; see §5 for a locked ZFS destination.

- **Archive to Ceph:** restore from a root shell. The Ceph deployment guide sets `OPENSSL_CONF` in
  `/etc/environment` so that the restore uses wolfProvider for the Ceph connection. A web-interface
  or API archive restore does not inherit this setting. This restriction does not apply to ZFS or LUKS.
- **PBS restore, every destination:** complete the `/usr/bin/pbs-restore` wrapper in Node Configuration
  and Recovery guide §2. It enables wolfProvider for chunk decryption from both the command line and
  the web interface or API.

**Important:** do not configure `pvedaemon` to use wolfProvider. This breaks web-interface and API
logins; see Node Configuration and Recovery guide §1.

#### Check wolfProvider during restore

During the restore in §2.4, run the applicable check from a second shell on the destination node while
data is transferring:

```bash
# from a Proxmox Backup Server datastore, on every destination:
grep -c libwolfprov /proc/$(pgrep -n -f '^/usr/bin/pbs-restore' | head -1)/maps  # -> non-zero
# from a vzdump archive, on a Ceph destination:
grep -c libwolfprov /proc/$(pgrep -x vma | head -1)/maps                         # -> non-zero
```

**Note:** wolfProvider loads on first use. Retry an initial `0` once the transfer is progressing;
a sustained `0` indicates a failure.

### 2.4 Restore onto the FIPS storage

Use the appropriate source below, then complete §2.5.

#### From a backup archive

The deployment guides restrict `local` to `vztmpl,iso`, so a copied `vzdump` archive cannot be selected
in the web interface. Restore it by path from a root shell; an API token cannot pass an arbitrary
filesystem path.

```bash
# on the destination node:
# virtual machine:
qmrestore <archive> <new-vmid> --storage <fips-storage>

# container:
pct restore <new-vmid> <archive> --storage <fips-storage>
```

#### From a Proxmox Backup Server datastore

Copy the source deployment's encryption key to the destination (§1.2). If the destination already
uses the same datastore, register a second storage with the source key. A wrong key allows snapshot
listing but fails at restore (§5).

```bash
# on the destination node:
pvesm add pbs <name> --server <pbs-host> --datastore <datastore> \
    --username <user>@<realm> --password <password> \
    --fingerprint <pbs-fingerprint> --encryption-key <keyfile> --content backup
qmrestore <name>:backup/vm/<vmid>/<snapshot> <new-vmid> --storage <fips-storage>
```

### 2.5 Set guest options and check disk placement

After either restore path, set the guest options and check its storage:

```bash
# on the destination node:
# virtual machine:
qm set <new-vmid> --boot order=scsi0
qm set <new-vmid> --onboot 1
qm config <new-vmid>                    # -> every disk on <fips-storage>

# container:
pct set <new-vmid> --onboot 1
pct config <new-vmid>                   # -> every mount point on <fips-storage>
```

**Important:** restores retain the source guest's `onboot` setting. Set it to `1` as above so that
the node's recovery procedure starts the guest.

Continue at §4.

## 3. Alternative: `qm remote-migrate`

Where both deployments are reachable and an API token exists on the destination, the guest can be
moved directly. Proxmox VE marks [`qm remote-migrate`](https://pve.proxmox.com/pve-docs/qm.1.html)
experimental; use §2 for backup and restore.

Record the verification checksums in §2.1 before stopping the guest.

**Important:** a `zfspool` target accepts only ZFS send streams. For Ceph RBD, LVM-thin, or directory
source volumes going to ZFS, use §2; `remote-migrate` fails with
`no matching import/export format found for storage <fips-storage>`. Directory-backed destinations,
such as the LUKS deployment's, are unaffected.

This command runs on the **source** node. With `--online 0` the guest must be stopped first, or the
command refuses with `can't migrate running VM without --online`:

```bash
# on the source node:
qm stop <vmid>
qm remote-migrate <vmid> <new-vmid> \
    'apitoken=PVEAPIToken=<user>@<realm>!<tokenid>=<secret>,host=<destination>,fingerprint=<tls-fp>' \
    --target-storage <fips-storage> --target-bridge <bridge> --online 0
```

**Note:** an aborted migration leaves a locked placeholder and any transferred disks on the
destination. See §5 before retrying.

Set `onboot` for the recovery procedure, as in §2.5:

```bash
# on the destination node:
qm set <new-vmid> --onboot 1
```

`--delete` defaults to `0`, leaving the source guest stopped and available for rollback.

## 5. Troubleshooting

### `unable to change passphrase - no tty` — converting a key without a terminal (§1.2)

The command requires a terminal. Clear `PBS_ENCRYPTION_PASSWORD` so that it prompts for all three
answers, then supply them through a pseudo-terminal:

```bash
printf '%s\n%s\n%s\n' "$OLD_PASSPHRASE" "$NEW_PASSPHRASE" "$NEW_PASSPHRASE" | \
  env -u PBS_ENCRYPTION_PASSWORD \
  script -qec "proxmox-backup-client key change-passphrase <keyfile> --kdf pbkdf2" /dev/null
```

Confirm the key's `kdf` field as in §1.2.

### `encryption root's key is not loaded or provided` — locked ZFS destination (§2.3)

No volume is created, but a stub guest configuration remains. Confirm with
`pvesm list <fips-storage> --vmid <new-vmid>`, unlock the storage per the deployment guide, clear the
stub configuration (next entry), then retry.

### `VM <new-vmid> already exists on node '<node>'` — failed restore (§2.4)

A failed restore leaves a stub configuration holding the target VMID. Remove it before retrying:

```bash
# on the destination node:
qm destroy <new-vmid> --purge 1
```

### `wrong key - unable to verify signature` — wrong PBS key (§2.4)

The datastore was registered with the wrong encryption key. The error identifies the mismatched
fingerprints. Re-register the storage with the source deployment's key (§2.4).

### `Guest with ID '<new-vmid>' already exists on remote cluster` — aborted `qm remote-migrate` (§3)

An aborted migration leaves a locked placeholder at the target VMID on the destination; `qm destroy`
alone reports `VM is locked (create)`. Clear it:

```bash
# on the destination node:
qm unlock <new-vmid> && qm destroy <new-vmid> --purge 1
```

The placeholder references no disks, so `qm destroy` leaves any transferred volumes on the destination.
List and remove them before retrying:

```bash
# on the destination node:
pvesm list <fips-storage> --vmid <new-vmid>
pvesm free <volid>                      # for each volume listed
```
